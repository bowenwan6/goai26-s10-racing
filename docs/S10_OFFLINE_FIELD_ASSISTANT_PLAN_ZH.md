## 1. 结论与交付目标

可以在现有手机建图网页上增设“现场验收”入口，不需要重做原生 App，也不需要户外互联网。手机连接 `<ROBOT_WIFI_SSID>`，打开 `http://10.21.41.1:8080/field`；这个 `/field` 是拟新增地址，目前尚不可用。

第一版交付三项：

1. 指定地图的静止与人工遥控定位验证记录，包含自动检查及人工叠合确认。
2. 静止、直行、转向的有效短录制，能供后续真机数据适配与影子策略回放。
3. 与地图版本绑定、带质量证据的首段真实航点。

“只带手机”实际是 **手机＋原厂手柄＋现场人员**。网页不控制行走；结束任务、停止录制均不等于停车或急停。首轮只做安全平地短段，不做楼梯自主运动或全程竞速。

## 4. 户外无互联网：怎样保证可用

### 区分两种断网

- **无互联网**：正常工作条件。网页、脚本、字体/图形库、地图预览、帮助页和报告全部由机器人提供；不用 Tailscale、云登录、在线地图或 CDN。
- **手机与机器人 Wi-Fi 断开**：不能再发指令或看实时数据；已被机器人接受的有界任务继续执行并留档，连接恢复后查询结果。未被接受的操作不得冒充已执行。

保留 HTTP 局域网页，而不把首版设计成依赖 Service Worker 的 PWA。Service Worker 通常需要 HTTPS 安全上下文，手机访问 `http://10.21.41.1` 不属于 localhost 例外；在这个地址承诺离线后台同步不可取。局域网服务器本身不依赖互联网就能提供页面。[MDN：Service Worker API](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API)

HTTP 也不等于加密安全：保留专用 Wi-Fi、网页登录、CSRF 和最小后台权限，不把 8080 暴露公网；多人共用不可信网络时应另做本地 HTTPS/证书方案。手机不需要保存 SSH 密码。不能因“在内网”删除认证。

### 任务的主本放在 106，不放手机

拟新增 `field_worker`：作为机器人端受监督的独立进程，负责执行任务；106 本地 SQLite 保存任务、事件和幂等键，文件保存录制/报告。102 只做请求转发、界面和可重建预览缓存，不做双主任务数据库。

- 请求接受后尽快返回 `job_id`，长任务不占着手机 HTTP 请求等完成。
- 同一幂等键＋相同请求返回同一任务；相同键不同内容拒绝。两个手机也不能重复切图/启动录制。
- 任务记录包括机器人、地图版本、boot ID、定位会话、开始/截止时间、阶段、产物与失败原因。
- 手机锁屏不影响已接受任务；页面恢复、登录过期重新登录后查询同一任务。
- 断线后只自动恢复查询，**不自动补发离线积压的“切图/开始/标点”操作**。
- 网页服务重启与机器人重启区别处理。前者重新查询 106；后者把中断录制标为中断并检查残留文件，不能声称录制跨断电继续。
- 数据库事务用于任务登记的一致性；它不能让外部 `drmap` 操作也成为同一个原子事务。若切图后响应丢失，先对照真实 active map 和服务会话，不盲目再执行一次。[SQLite：Atomic Commit](https://www.sqlite.org/atomiccommit.html)

时间同步只依赖机器人内部既有同步链路，不把公网 NTP 可达性作为合格条件。时长使用机器人端单调时钟，证据保留 ROS 时间、接收时间和 boot ID；手机时间不是采集时间的基准。离线冷启动的时钟行为需要实测。

## 5. 定位、叠图和航点的实现细节

### 同一张图、同一时刻、同一参考点

1. 地图身份使用目录名＋内容清单/哈希＋坐标/标定版本，不能只比较名字。大文件校验在准备阶段做，现场复核变更后再计算，避免每次刷新重复扫描整张地图。
2. 预先把本次地图生成适合手机的抽样/分级显示资源；仅降低显示负担，不滤改厂商 SLAM 使用的原始 PCD。
3. 扩展当前状态结构，保留完整四元数、`child_frame_id`、协方差和来源；不能从现有只含 XYZ/yaw 的网页结构推断全部语义。
4. 当前定位扫描从实际可用的定位输出话题选取，例如既有观察脚本使用的 `/ALIGNED_POINTS` 等，核实帧名和消息时刻。跨帧时使用经核验的时间对应变换；查不到则显示“无法叠合”，不能硬贴上去。
5. 不因为 `/ODOM.header.frame_id == map` 就认定全局定位成立；还要官方状态新鲜、正常/全局、地图和服务会话一致。
6. 位姿跳变是重要证据，但不是所有 map 系跳变都代表坏驱动：全局定位修正本身可能使 map 系位姿不连续，需结合状态分析。ROS 约定还明确机器人基座参考点可能因平台而异，因此必须查清 S10 的实际定义。[ROS REP-105](https://raw.githubusercontent.com/ros-infrastructure/rep/master/rep-0105.rst)

### 检查结果不冒充精度证明

检查报告分成“程序检查”“人眼确认”“未验证项”。30 秒静止窗口可说明状态是否稳定、是否出现丢定位，不能证明厘米级精度，也不能证明整条 300 米路线覆盖完整。

阈值使用版本化配置，区分网页显示阈值与策略输入门槛，不照搬现有网页约秒级刷新容忍度给控制使用。匹配误差、内点率等要确认实际含义和厂商配置才设门限；协方差为零也不自动代表可信。

图加载页面显示“已请求→切换地图→预处理→等待全局定位→等待人工叠合确认”的真实阶段和经过时间。厂商没有可信百分比时不编造进度百分比。超时显示诊断，不自动反复重启定位。

### 找不到初始位置怎么办

首版现场流程限定：回到地图覆盖内的明确位置，优先原建图起点附近并核对朝向。若仍不能全局定位，保存失败证据，停止后续合格标点。

“在地图上随便点一个初始位姿”不进入首版默认按钮：厂商初始化/重定位接口和坐标语义尚需验证。若希望从任意已扫位置开机，应单独补充“人工选择起始区域与朝向”功能，先核实官方接口、停稳条件及失败处理，再纳入验收；不能假定切图就一定自动找得到位置。

### 航点保存规范

- 后端收到标点请求后采集约 2–3 秒的新数据，而不是保存点击前浏览器缓存的最后一帧；最终时长与稳定门限经静止实测确定。
- 验证停稳、正常全局定位、地图/服务会话不变、源数据新鲜，姿态平均要处理角度绕回，不能直接算 179° 与 −179° 的普通平均。
- 保存：名称、顺序、XYZ、完整姿态、朝向、参考帧、地图哈希、标定版本、采样窗口、离散度、人工确认、楼层/路段类型及安全停靠备注。
- Z 表示经过核验的机器人参考点高度，不是地面高度，不使用为美观抬高的网页箭头 Z。
- 外参或参考点尚未核实，可以保存“待确认位置草稿”，但不可导出为已通过的导航路线。
- 先保留原始标点，再生成兼容 `real_transfer` 的审阅后路线；地图变更后失效重审。不同楼层或楼梯两端不能自动用一条平面直线连接。

## 6. 录制、质量检查与现有策略的关系

### 录制方案

优先在 106 本机用 ROS 2 的 rosbag2 记录原始消息，使用实机已安装且验证过的存储插件；MCAP 优先，但插件缺失时先验证可用替代或在出发前安装，不能到户外再在线安装。具体命令按实机版本的帮助和功能检查生成。

只录经核验的白名单，不使用无界的“录全部话题”。候选为 `/ODOM`、`/IMU`、实际策略所需的点云（需核对 `/LIDAR/POINTS_MERGED`）、定位对齐输出、匹配状态、`/tf`、`/tf_static` 和可选 `/elevation_map_raw`。逐项检查类型、发布者、频率、帧名和 QoS；所需数据不存在要记为缺项，不用虚构话题补齐。rosbag2 支持指定话题、QoS 配置和文件信息检查，但文件分卷不等于限制整个任务的总时长/总字节数，后者由 worker 另行控制。[ROS 2 rosbag2 官方说明](https://raw.githubusercontent.com/ros2/rosbag2/jazzy/README.md)

- 传感器订阅匹配实际 QoS，特别核对静态变换的持久性，避免“录制正常但没收到关键话题”。
- 初版每段 10–30 秒；总字节上限、磁盘保留空间和并发预算按 106 的实测带宽/负载确定，不能引用 102 的 38 GB 当保障。
- 正常结束录制并等元数据写完；逐话题检查实际记录量、时间范围、空洞和可读取性。文件存在、进程返回成功均不足以单独判定合格。
- 提供源数据与采集时间检查；消息数与预期频率只能支持缺失检测，不能无依据承诺零丢包。
- 录制失败保留部分文件并标记，不自动删原件；修复/重新索引针对副本操作。
- 预览、录制同时开启时测 CPU、内存、磁盘写入及定位/传感器输出变化，必要时先降低网页刷新，不降低原始采集要求来假装通过。

### 复用现有影子策略，不让网页一键开跑

现有 `real_transfer/ros_observer.py` 是有界观察与 JSONL 快照工具，不是完整原始 ROS 录制，缺少完整话题覆盖且可能重复写入上一帧点云。复用它的数据规范/检查思路，补 bag→标准观察数据转换，保留原始 bag 作为证据。

取得合格录制和航点后，在电脑离线回放到 `real_transfer`：检查位置/方向、时间、雷达与高度图输入，并输出“策略本来会给出什么建议”的文件报告。**不在实机当前 ROS 网络中播放 bag，不把建议发布为运动指令。**

已有实时高度图可复用显示，但接入策略前还要核对网格索引、中心/方向、Z 语义、未知格和厂商补地；不能把它直接改成我们的 13×9 输入就当作已验证。未知区域不能补零当平地。

影子回放用于检查数据兼容和保护逻辑，不是闭环物理仿真，不能证明真实碰撞安全。后续低速自主平地段仍需单独完成运动接口、唯一控制源、失效停车和手柄接管验收。

| 106 新 `field_worker.py` 及存储/校验模块 | 本地 SQLite、任务状态机、官方地图适配器、录制监督、位姿校验和报告 |
| 106 新受监督服务 | 启动 worker，与网页/SSH 会话解耦；出发前验证离线开机和用户服务生命周期 |
| `real_transfer/` 的只读适配工具 | 增加录制转换和报告衔接，不增加运动发布器，不自动填写未验证配置 |

服务器端统一操作互斥需要覆盖旧“开始建图/保存”和新“切图/录制/标点”；安全的只读查询可并行。外部厂商进程不遵守我们的锁，因此每个关键步骤前后仍需核对真实服务状态和地图身份，发现外部切换立即使验收结果失效。

地图切换前要求现场确认机器人停稳、手柄接管/急停可用，并检查无活动建图/录制、无冲突任务。零速度命令和日志“无目标”只是证据之一，不能当作物理停稳保证。回退地图也须重新满足停稳条件并明确确认，不因网络超时自动回退。

拒绝任意命令、任意路径、任意 ROS 发布和未验证地图名；录制/导出只访问任务目录。导出清单不包含 SSH 私钥、网页配置、密码或其他任务的敏感信息。下载鉴权，先提供小报告和航点，大文件采用流式传输及断点续传设计，不一次装进内存。

## 8. 实施顺序与验收关卡

| 阶段 | 工作 | 完成条件 |
| --- | --- | --- |
| A：核对实际版本 | 补齐 106 新版源码/接口、录制工具、空间、帧/外参信息；保存源码与配置版本基线，整合最新高度图改动 | 知道将改哪些文件、哪些原功能必须保持；不覆盖他人的新代码 |
| B：离线任务底座 | 独立 worker、持久化、幂等、互斥、认证、查询/导出；先用模拟后台测异常 | 刷新、双击、响应丢失和服务重启不重复启动操作；中断如实显示 |
| C：自检＋新图验证 | 新图预览、官方切图阶段、30 秒检查、人工叠合与失败记录 | 在原场地能够区分加载成功、全局定位成功和人工确认；错误状态不能绿灯 |
| D：录制＋航点 | 限时原始录制、质量报告、受控标点、地图版本绑定、策略输入导出 | 三类片段可读、缺项可见；真实平地航点参考点明确，地图变化会失效 |
| E：真实手机离线验收 | 原厂手柄有人值守，无 WAN、手机不借蜂窝网的完整流程与重连测试 | 不带电脑/Codex也能完成并取回三个交付物，且原建图/高度图不回归 |

优先顺序是“可靠任务底座→自检与定位→录制与航点→真实手机验收”，而不是先画完六个按钮就出发。出发前完成依赖安装、目标图显示资源、离线帮助及启动链路检查。

### 必测场景

1. 手机实际使用的 Safari/Chrome：关闭蜂窝数据、机器人没有 WAN，首次打开页面、登录、地图显示和下载都可用；需要的局域网权限允许。原有 Mac Clash/Tailscale 配置不作为现场依赖，也不因本功能而修改。
2. 同一按钮双击、两部手机同时提交、请求被接受后 HTTP 响应丢失：只存在一个对应任务，重连能查到它。
3. 手机锁屏/关闭页面/重新连接：已接受的录制到机器人端截止时间自动收尾；页面不保留过期绿灯。
4. worker/网页服务重启、模拟掉电：历史任务保留，中断不会被误报成功，不自动重切地图或重新开始录制。
5. 磁盘不足、记录文件不可读、某必需话题为零消息或时间戳跳变：明确失败并保留可恢复证据。
6. 假的“局部但坐标很稳定”、陈旧厂商日志、地图被外部更换、缺失外参、姿态不合法：禁止合格标点和合格导出。
7. 实机比较只定位、加预览、加短录制的负载和数据频率；验证旧建图保存、新高度图不受回归影响。
8. 检查新代码不存在运动发布器/导航目标入口；所有“停止录制/结束”文案明确不停车。

故障注入先在本地模拟/测试进程做，不直接在运行中的机器人上拔电、改时钟或故意写满磁盘。实机切图、重启和物理断网验收放在有人值守、停稳后另行执行，不属于本轮调研。

## 9. 完成部署后，你在现场的最短流程

1. 带手机与原厂手柄，机器人回到本次已扫区域内的明确位置；开机，连接机器人 Wi-Fi，即使系统提示无互联网也保留此连接。
2. 打开网页“现场验收”，运行自检。确认设备是 48 号、目标图正确，处理失败项。
3. 手柄控制停稳，确认无人发导航任务，点击加载 fullrun；等待预处理和全局定位。
4. 运行静止检查，观察地图与实时扫描、地标和朝向是否一致；通过后人工确认。失败只导出诊断，不往下假通过。
5. 先静止录制，再在安全平地用手柄直行、转向各录一段。定位掉了就人工停稳，留故障证据，不继续合格标点。
6. 用手柄到首段起点、转弯点、终点/安全停靠点，每次停稳后点击标点并命名。
7. 手柄停稳机器人，结束任务，查看缺项，下载报告与航点；大录制保留机器人上可稍后下载。

当次目标不是“一键自主跑全程”，而是带回可用的定位证据、录制和真实路线。之后离线影子策略核对通过，再安排有保护的自主平地短段；楼梯和全程放后面。
