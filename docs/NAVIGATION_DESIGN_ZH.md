## 1. route_v2 路线跟随与局部规划

*（原 `ROUTE_V2_PLANNER_ZH.md`）*

状态：**仅离线/单元/运动学仿真验证**，未上机、未接 MuJoCo、未经实云回放。默认行为不变：不给 `route_v2_path` 时，follower 与 native runtime 走原来的 Course + LocalPlanner + 0.35 m 走廊逻辑。

### 1. 解决的问题

| 旧行为 | route_v2 行为 |
|---|---|
| `Course.lookahead_point` 的 carrot 在“机器人→当前 WP”直线上，绕障后直切下一 WP | carrot 在**示教中心线**（`segments[].centerline`）的横向偏移路径上，绕障后回到中心线 |
| `LocalPlanner` 只按与目标方位的偏差打分，单帧、全堵无搜索 | Frenet 横向偏移采样 + 足迹扫掠碰撞 + 横向代价；全堵时有界 A*；A* 失败即 STOP |
| native 距当前直线段 >0.35 m 即 fault | 用该段 `corridor_half_width + 0.10 m`（相对中心线，含 z 楼层校验）；旧 draft 仍为 0.35 m 原规则 |
| gait 来自 WP `kind` | gait 来自 route_v2 段（`kind` = 驶入该 WP 的段的 gait），settle→switch→confirm 不变 |

### 3. 规划算法（每 tick）

1. **有序到点**：只检查当前目标，XY ≤ `radius_xy` 且 |z_base − (z_ground+offset)| ≤ `tol_z` 才推进，每 tick 至多一个。
2. **投影**：`RouteTracker` 在 `[s−1.0, s+2.5]`（不越过未到达目标 s+1.0）内投影；只有距离近似相等的**不同局部极小**（如 switchback 两腿、内角两侧）才按与上次 s 的接近程度裁决。
3. **候选**：目标偏移 `d_t ∈ linspace(−W, W, 17)`（0.1 m 间隔）（`allow_detour=false` 时只有 0）；五次多项式从当前 d 过渡到 `d_t`，长度 `max(1.0, |Δd|/0.5)`，水平视界 3.5 m，不越过未到达的 WP（接近 WP 时偏移在 1 m 内回零并以 WP 点为终点）。已选中的过渡**锚定在选中位置**，由纯追踪跟随（每 tick 重新以机器人为起点、或以实测航向为初始斜率都会出问题：前者永不产生横移，后者与纯追踪形成正反馈）。
4. **碰撞**：矩形足迹 0.9×0.5 m + 0.05 m 余量，按纯追踪实际会采用的航向（指向前方 lookahead 点）扫掠；起点航向差 >10°（与控制器原地转向阈值一致）时扫掠整个转动角。OBSTACLE 与 UNKNOWN 都阻挡，例外：机器人当前足迹内豁免；未来足迹**后半部**落在当前车头之前的 UNKNOWN 不阻挡（车尾只跟随车身已覆盖/旁边的地面）；不许绕行的 stairs 段沿示教线 UNKNOWN 不阻挡（见 §7）。候选有效条件：前 `commit_length`（flat 1.0 m / stairs 0.4 m）无碰撞。
5. **代价**：`w_obs·proximity(足迹到障碍/未知) + w_free·(1−free/H) + w_lat·|d_t| + w_smooth·|d_t−prev| − w_progress·free/H + 换边惩罚`，默认 1.0/5.0/1.0/0.3/0.5/1.0；`w_lat > w_smooth` 保证无障碍时 d=0 胜出并回线；上一目标仍有效且代价差 < 0.3 时保持（防止原地转向引起的来回切换）。
6. **兜底**：全部候选无效且允许绕行 → 6×6 m 窗口 8 邻接 A*（圆盘膨胀 0.3 m、走廊外禁止、横向偏移计入代价、目标为前方 5→3 m 中心线点；若都在障碍阴影 UNKNOWN 中则取可达**已知**格中 s 进展最大者，至少 0.8 m）；再用矩形足迹复检。若所有候选都只是被 UNKNOWN 挡住、需要 >10° 转向且原地转向扫掠无碰撞 → `ALIGN`（零前进，原地转向，下一帧看清弯道后重新规划）。失败 → `BLOCKED` + 原因。`allow_detour=false` → 直接 `BLOCKED(centerline_blocked_detour_forbidden)`。从不规划倒车，输出 vx ≥ 0。
7. **速度**：`min(控制器上限, 段 speed_limit) × speed_scale`；speed_scale 随“到第一个真实障碍的距离”递减（下限 0.3），未知区域只要求超过 commit 长度（再往前靠机器人移动后继续观测）。
8. **看门狗**：处于运动状态但 s 20 s 未前进 0.1 m → `BLOCKED(no_route_progress)`；native router 自身 15 s 无进展 fault 仍在。

#### 局部栅格

- 世界对齐、以机器人为中心、0.1 m、8×8 m，格点对齐世界网格（多帧融合时每帧栅格化结果缓存复用）。
- 高度图：孤立无效格（8 邻域中 ≥6 个有效且高差 ≤ 当前台阶上限）用邻格中位数补；车头前 0.9 m 内无效格 = UNKNOWN（即使扫描线扫过），更远的无效格与 ROI 外一样按扫描处理；相邻格高差 > `max_step_flat` 0.12 m / `max_step_stairs` 0.22 m / 不许绕行 stairs 段 `max_step_taught` 0.35 m 时，标记**离机器人脚下地面更远**的那一格（箱顶、落差下沿）。
- 机器人当前足迹外扩 0.15 m 置为 FREE（Nav2 式 footprint clearing：车身下方与紧邻处被自身遮挡）。
- 扫描：NaN bin 不产生任何信息；有限距离的端点（≤6 m）标 OBSTACLE，但只标 bin 中心射线两侧 ±0.06 m（子射线仍全部用于标记空旷；原先整格 5° 都标会把示教线旁 0.39 m 的立柱抹进路线）（保守：端点可能只是地面观测尽头），端点后为 UNKNOWN；+inf 视作 4 m 内无回波。stairs 段忽略扫描（台阶立面在机身高度带内），ROI 外即 UNKNOWN。
- 融合（`fuse_frames>1`，默认 1）：新帧对其“已知”格覆盖旧帧；新帧 UNKNOWN 不抹掉旧帧 FREE（如机身下方自遮挡）；SCAN_CLEAR 只能升级 UNKNOWN；超过 `max_age` 2 s 过期；z 跳变 >0.5 m 清空。

#### 地形交叉检查（只 warn/hold，从不切 gait）

- flat 段：俯仰 ≥12° 持续 0.5 s → **HOLD**（零速）；高度图呈台阶/坡（rise≥0.12 m 且跨度≥80%，或拟合坡度≥12°）→ WARN。
- stairs 段：俯仰<4° 且高度图平坦 → WARN。
- runtime 与 follower 核心各自运行；HOLD 持续会触发 router 的 15 s 无进展 fault，需要人工处理。

### 4. 仿真/harness 入口（无 ROS）

```python
from s10_auto_nav.route_follower import RouteFollowerCore
core = RouteFollowerCore.from_file("route_v2.json", body_z_offset=0.42, native=True)
out = core.step(t, (x, y, z_base, yaw), height13x9, valid13x9, scan72, scan_angles,
                pitch=pitch, roll=roll, current_gait="flat")   # 或 0x3002/0x3003/None
vx, vy, wz = out.command            # 机体系 m/s, rad/s；非运动状态时为 0
out.gait_request, out.gait_code     # 驶入当前目标的段的 gait
out.status, out.reason              # RUNNING/DETOUR/ASTAR/GATE/ALIGN/BLOCKED/OFF_CORRIDOR/
                                    # HOLD_TERRAIN/WAIT_GAIT/STALE_INPUT/DONE
out.target_id, out.segment_id, out.s, out.d, out.reached, out.plan.path, out.plan.carrot
```

- `height13x9`：机器人 yaw 系（x 前 y 左）、相对机身参考点的高度，X-major，与 `real_transfer.geometry.height_grid` 相同；`valid13x9` 为有效掩码（未知可为任意值）。
- `scan72`：`conservative_scan` 语义（NaN=未知）；`scan_angles` 省略时用 bin 中心 `−π+(i+0.5)·5°`。
- 没有新观测的 tick 传 `None`；0.5 s 无新观测 → `STALE_INPUT`。
- `current_gait` 不等于所需 gait → `WAIT_GAIT`（harness 应模拟 router：停稳→切换→确认后再给速度）。
- 参考实现：`route_sim.run_closed_loop(core, KinematicBody(...), duration=..)`。

### 5. native 用法

`native_transfer/runtime.py --route <route_v2.json>`（旧 draft 仍可用）。runtime 自动：点表与 gait 取自路线段；每目标限速 = 段 `speed_limit`（只降不升）；follower 设置 `route_v2_path` 与 `route_v2_body_z_offset`；扫描角度在 route_v2 模式下取 bin 中心；走廊 = 段宽 + 0.10 m 且 z 必须匹配本层；地形交叉检查结果写入日志 `sensors.terrain_check`，HOLD 时置零指令。**感知准入门槛未放宽**（仍要求 117 格全有效且 72 bin 全已知才交给 follower）。

### 6. 验证情况

已验证（本机，`python3 -m pytest`）：
- 单元：投影（直线/直角/switchback/两层楼）、跟踪器连续性、合同校验、转换、逐 WP 半径；规划器（无障碍 d=0、线上障碍在走廊内绕行、不许绕行则停、全堵走 A*、A* 失败停、UNKNOWN 阻挡、全未知不“发明”空地、原地转向扫掠、栅格构建/融合）；router 按段 gait 与 settle→switch→confirm、限速只降不升、段宽走廊、层不符拒绝、旧 0.35 m 规则逐字保持；follower 节点分支（ROS 以测试内 stub 代替）。
- 运动学闭环（独轮车+小横移，native 增益 0.2 m/s、10° 原地转向阈值）：直线上 0.4 m 箱体，绕行最大 |d|≈0.77 m < 0.8 m 走廊，箱后回线 |d|<0.1 m，全部 WP 到达，无倒车，旋转矩形机身与箱体无重叠；另测 8 种箱体位置/尺寸/偏置组合：6 种绕行并回线；2 种（起步正前方 1.5 m 的箱体、0.7 m 宽箱体使 0.8 m 走廊只剩约 0.15 m 余量）安全停车 `BLOCKED(astar_path_fails_footprint_check)`；8 种均无机身接触、无倒车。
- 真实路线 `tools/wp_match/out/route_v2.json`（30 WP / 29 段 / 256.6 m / z −0.46→5.88 m）：可加载；每个中心线点投影回自身；带 5 cm 噪声与整段走廊宽度正弦偏移的连续跟踪无跳变、无层错配（路线自身最近的非相邻段水平距离 3.6 m）。测试通过 `S10_ROUTE_V2` 环境变量或默认路径定位，缺失时跳过。

未验证 / 已知局限：
- 未在 MuJoCo、实云回放或实机上运行；参数（权重、commit 长度、步高阈值）只在合成场景调过。
- 单帧 13×9 高度图只覆盖 1.8×1.2 m：ROI 外只有扫描“无机身高度回波”证据（SCAN_CLEAR），**看不到 ROI 外的负障碍（坑/落差）**；`require_ground_within` 可强制近距离必须是高度图验证过的地面，但单帧下会阻止几乎所有绕行，建议配合 `fuse_frames>1` 并用实云验证后再开。
- stairs 段只用高度图，视野约 0.75 m，速度随之保守；楼梯踏步 >0.22 m/0.15 m 格会被判为障碍而停车。
- 障碍面距车头 <约 1 m 才出现时（例如起步正前方 1.5 m 的箱体），或障碍几乎占满走廊时可能无可行候选且 A* 复检失败 → 安全停车而非绕行。
- A* 以圆盘近似机身再用矩形复检，窄通道可能保守失败。
- 扫描端点一律视为障碍（conservative_scan 无法区分“观测尽头”和“真实障碍”），稀疏地面会造成假障碍/提前绕行或停车。
- 地形交叉检查阈值未用实数据标定；高度图证据只报警不拦截。
- 回线后的纯追踪在 WP 处仍会按 0.5 m 刹车距离减速（与旧 Course 一致，carrot 不越过未到达 WP）。

| B 楼梯 / 乱石 / 石笼 | 立面格无效、石块台阶 >0.22 m 被当障碍 | 不许绕行的 stairs 段：沿示教线 UNKNOWN 不阻挡；台阶上限 0.35 m | **安全取舍**：这类段上新出现的、矮于 0.35 m 的物体看不见；更高的（人）仍会停 |

已知未解决：
1. **到点前最后一段**：机器人在航点前仍横向偏 ~0.4 m 时，`min_horizon` 内直接对准航点的直线检查失败（需 ~50° 转向）。应让 gate 前的回线更早完成，或到点检查改为经过航点的走廊判定。
2. **0.12 m 路沿**：需要高度图多帧融合后再标定 `max_step_flat`，或用先验地图变化检测。

**调试中途曾停在**：WP23→WP24 沥青段一个 ~0.3×0.2 m、比四周低 10–16 cm 的凹坑（可能是排水口或地图噪声），平地台阶上限 0.12 m 判为障碍，而建图时机器人直接压过。

**下一步建议（需要决定）**：用先验地图做变化检测（VT&R 思路）——对示教走廊预存地面高度（`match_wps.py` 已算出），把“观测高度 − 先验高度”的突变而不是原始高度突变当作障碍。这样示教时走过的台阶、石块、凹坑都不再误报，而新出现的箱子、人、路障都会被发现；也能撤回上表中 0.35 m 的安全取舍。

## 2. rl_nav 路线跟随器与鲁棒性方案（v3）

### 0. v3（2026-09-19，当前）：第一版就是名义控制器，鲁棒只在测到偏离时介入

**为什么推翻 v2。** v2 在第一版之上叠了一层层"一直开着"的保护（台阶上的落差/侧落差急停、卡住回退重试、局部栅格 A* 回线、跟线门控）。结果是在**没有任何扰动**的仿真里也停车：

| 位置 | v2 的表现 | 原因 |
|---|---|---|
| B 下段第一级台阶 | 3 个种子里 2 个在 WP05 后停住（"climb made no progress"） | 路线以约 55° 斜穿第一级立面，斜着的立面在 13×9 高度网格里留下一串未知格：侧落差判成"左边有落差"、前方判成"空洞"，1150 在"左转—右转"之间来回，永远不前进 |
| WP18→WP19 | 无扰动矩阵停车（"route blocked and no way round"） | 下台阶后跟随器报 BLOCKED，局部 A* 在粗糙地面找不到路，回退模式互相踢皮球 |
| 定位偏置 0.2 m | WP13 一开始就卡住 | 同上，局部栅格把地形读成障碍 |

第一版在这些地方都能直接过。所以 v3 **把第一版的控制器原样作为名义行为**（模式、参数都不变，保证"不比第一版差"），第一版真正缺的只有一件事：机器人不在路线应有的位置时怎么办——被推开、路上有地图没有的东西、打滑、原地不动。这部分作为**只在测到偏离时才介入**的恢复层加上去，一回到路线就交还给名义控制器。

#### 0.2 恢复层：只在测到偏离时介入

| 触发（机器人自己测得到的量） | 动作 | 退出 |
|---|---|---|
| 走廊里有地图没有的东西：LiDAR 点比地图表面（0.3 m 内最高处）高出 0.2 m 以上（`map_check`，地图变化检测） | **DETOUR**：在地图栅格上做 A*（`map_planner`：0.1 m 栅格，未知/障碍/>0.3 m 落差为危险，离危险 < 0.4 m 不可走，坡 > 15° 或坎 > 0.1 m 不走，看到的新障碍点一并封掉），目标是障碍之后的路线点，纯追踪跟随 | 回到路线（横向 < 0.25 m）且过了目标段 → WALK |
| 离路线 > 0.8 m，或回线的直线穿过地图危险区 | DETOUR：同上，目标是前方 1–3 m 的路线点（永远不进下一个台阶区） | 同上 |
| 8 s 没有沿路线前进 | 先后退 0.3 m（身后在地图上是空的才退），再 DETOUR（地图 A* 重新规划） | 同上 |

| 绕不过去（如窄通道里站着人） | **WAIT**：停车，每 1 s 重新检查/规划；障碍离开就继续 | 30 s 仍不通 → HOLD（等人） |
| 1150 在台阶上遇到新障碍 | 原地停（1150 不能绕），WAIT | 同上 |

偏离小于 0.8 m 且回线方向没有危险时，不启用任何新逻辑——第一版的追线本身就会把机器人拉回来。

试过但没有合入：无台阶横坡上把爬升修正从 12° 放宽到 25°。运动学单测里能压住侧滑，物理仿真里 1150 在 WP29→WP30 横坡上照样下滑约 1 m（它几乎不会右转），没有证据支持就不改。

#### 0.3 调研依据

- 地图做先验、传感器只检测"变化"：地图变化检测（map-based change detection）是长期运行机器人的常规做法；这里逐点比较 LiDAR 与地图表面，给定位误差留 0.3 m 余量。
- 全局规划在先验地图上、局部只处理新障碍：Nav2 的全局代价地图 + 局部代价地图分层（Macenski 2020/2023）；地图 A* 使用代价感知栅格（Smac 规划器思路），把新观测到的障碍写入临时层。
- 名义控制器不因保护层变差：保护只在监测量越界时接管（run-time assurance / simplex 架构的思路），越界量都是机器人可测的：横向误差、前进进度、地图变化、速度。

#### 0.4 验收结果（GPU 服务器 MuJoCo 全程，c02d598）

两个版本都在同一台服务器上跑，用同一张地图、同一对 policy（J3100 步行、1150 台阶），只换随机种子（传感器噪声、点云丢点）。腿式 policy 对微小数值差异很敏感：同一个种子在 Mac（ARM）和服务器（x86）上结果不同，所以只看多种子的完成率。v3 的仿真还按真机 SDK 的方式切换 policy：J3100 → 1150 边走边切，1150 → J3100 要经过 0.25 s 的 SafeHold。第一版的仿真是瞬间切换。

| 全程 WP01→WP30 | 第一版（24 个种子） | v3 c02d598（32 个种子） |
|---|---|---|
| 跑完 | **4/24** | **19/32**（上一版 49fd514：23/32） |
| 翻倒 | 11（WP15 横坡 10、WP11 岩脊 1） | 5（B 楼梯 3、WP27→WP29 高台 2） |
| 停车 / 卡住 | 9（WP14 坎 4、WP11 岩脊 2、WP24→25、WP28→29、WP29→30 各 1） | 8（WP24→25 缓坡 3、漏打 WP04 或 WP11 后无路可回 2、WP11→12、WP27→28、WP28→29 各 1） |
| 跑完的用时 | 723–750 s | 611–655 s |
| ≥1 s 的停顿 | 3–9 次 | 0–2 次 |
| 航向来回（0.5 s 平滑后 \|ω\|>0.1 rad/s 换号，每 100 m） | 116–126 | 62–78 |
| 平均速度 | 0.38 m/s | 0.43–0.45 m/s |

v3 的"停车"是按设计停下并报告原因（例如漏打的航点在 J3100 不能走的地形上），不乱走。第一版的"卡住"是 45 s 没有沿路线前进。

鲁棒性测试：全程加一种扰动，每种 4 个种子，共 **14/28** 跑完。

| 扰动 | 跑完 |
|---|---|
| 定位偏置 0.1 m / 2° | 1/4 |
| 定位偏置 0.2 m / 3° | 2/4 |
| 定位噪声 3 cm / 1°（每帧） | 2/4 |

失败原因分布：翻倒 7 次，其中 B 楼梯 4 次、M09 台阶平台 1 次、WP14 坎 1 次、高台 1 次。停车 7 次：漏打 WP04 后停车 3 次（都是 seed 3），WP24→25 缓坡 2 次，B 楼梯下段 1 次，WP11→12 1 次。被推开和放箱子时，地图 A* 回线和绕行都起了作用；定位误差主要伤在 B 楼梯。

**剩下的问题**，按风险排列：

1. **B 楼梯（WP05→WP08）**。v3 无扰动 32 次里失败 3 次，扰动测试 28 次里 5 次。第一版全程 24 次都过了 B 楼梯，它的失败都在后面的路段。这个差别不显著：只看最终版 Fisher p = 0.25，v3 三个版本合计 10/80 时 p = 0.11。
   - 分段实验里，第一版从 WP03 起跑（A 楼梯 → 平台 → B）也会在 B 楼梯下段翻倒，v3 没有。
   - 从 WP05 起跑时两版都没有失败。去掉转向限制或去掉 ALIGN 侧移，同样都没有失败。
   - 注意：分段运行里随机种子几乎不改变轨迹，因为传感器噪声影响不到跟线以外的模式。v3 的 32 个种子跑出同一条轨迹，第一版只有约 6 条不同的轨迹。所以分段结果只能当个例看；以后做分段对比要加定位噪声，让每个种子真的不同。
   - 失败时 1150 斜着顶在立面上停住（第三跑立面与前进方向差 17–24°），然后侧滑下 2–4 m 的边。两版都有这个风险，根源是 1150 policy 的余量。
2. **WP27–WP29 高台**：1150 在坡上后滑，翻倒或 25 s 上不去（停车）。
3. **WP24→WP25 缓坡**：只停车、不翻倒，见 §0.2。

视频：仿真地形每个区域只有一种颜色，台阶在画面里看不出来。视频叠加层现在把路线经过的每一级台阶画成品红横条（按地图检测到 43 处），走近时标出高度（s10-rl-sprint 5fa5f49、b80440d，只影响视频）。

### 附：v1/v2 计划（历史记录，已被 v3 取代的部分见 §0）

### 1. 原则

1. 路线可以优化，但每一处修改在真机上都要成立。地图（v3 点云）只提供**先验**：哪一段需要换 policy、台阶大概在哪、朝向大概多少。**是否进入、朝哪对准、何时退出，都由现场感知决定。**
2. 不依赖仿真真值，也不依赖定位绝对准确：目标是在定位偏差 0.3 m / 5° 时仍能完成。
3. 偏离路线时由算法纠正（代价感知 A*），不做"盲跟示教线"。
4. 沿用 `strategy.Router` 的不变量：任何时刻只有一个指令源；传感器过期、翻倒、力矩持续超限就停；恢复有次数上限。

### 2. 仿真版里哪些做法到真机不成立

| 仿真做法 | 真机上的问题 | 真机做法 |
|---|---|---|
| 台阶区用 MuJoCo 地形真值沿中心线算出 | 真机没有真值 | 离线从 v3 点云地形标注（先验），现场用高度网格确认台阶边 |
| 手工改线（overrides）照着 MuJoCo 画 | 线本身画在同一张地图上，真机同样成立；问题是盲跟：地图误差 + 定位误差会让机器人偏离线 | （v2）验证过的手工线作为冻结段保留；偏离由现场感知纠正（实测台阶边对准、居中、A* 回线）；其余段落算法生成 |
| 对准方向 = 路线切线 | 定位偏航 5° 就会斜着上台阶 | 对准实测台阶边的法线（RANSAC 拟合） |
| router 回线时绕过规划器，盲跟示教线 | 看不见障碍 | 代价感知 A* 回线（按当前 policy 能力设代价），A* 失败才停车 |
| 退出台阶区看弧长 s | 定位误差会提前/延后切回 | 高度网格确认：机身下和前方 0.3 m 没有台阶边，高度接近上层平台 + 俯仰 < 5° |
| WP06、WP07 在仿真里挪了 0.6 m | 只在仿真地图成立 | 现场标点确认；途中靠居中和绕行保证安全 |
| 清掉路线 1 m 内的树冠方块 | 仿真地图专用 | 真机上由 conservative scan 的高度带决定，需要现场确认树冠高度 |

### 3. 架构

```
离线：v3 点云地形 ──► maneuvers.py ──► route_v2.json（官方 WP 不变，可附优化后的中心线）
                                   └► maneuvers.json（每个台阶区：s 区间、先验台阶边线/法线/高度、
                                                     需要的 policy、进入窗口、退出条件）
运行：定位 + /NAV_POINTS ──► 高度网格 13×9（多帧融合）
          ├─► EdgeTracker：立面格 → RANSAC 直线 → 距离 / 法线 / 台阶高 / 置信度，与先验做门限融合
          └─► 可通行栅格（按当前 policy 能力分级）──► RouteFollowerCore（Frenet 候选 + A* 兜底）
      strategy.Router：NAVIGATE → APPROACH → ALIGN → CLIMB_READY → CLIMB → VERIFY_CLEAR → HANDOFF
          └─► /cmd_vel + /strategy/joint_owner（official=J3100 / stairs_stable=1150）──► SDK runner
```

### 4. 算法选型（调研结论）

- **台阶边检测**：高度网格里找相邻格高差超过阈值的"立面格"，用 RANSAC 拟合直线得到边线；输出距离、法线、台阶高、内点数。这是阶梯建图和台阶跟踪里的常规做法（分段 + RANSAC 拟合、立面线拟合）。与地图先验做窗口门限（±0.5 m、±20°）：测量落在窗口内才采用，否则按先验慢速接近，仍找不到就停。
- **可通行性**：每格按坡度、粗糙度、台阶高三项加权（与 elevation_mapping 的 traversability 层同一思路）。阈值按**当前 policy**：
  - J3100：台阶 ≤ 6 cm（且速度 ≥ 0.5 m/s）、纵坡 ≤ 12°、横坡 ≤ 5°。
  - 1150：台阶 ≤ 18 cm、纵坡 ≤ 20°、横坡 ≤ 10°、只能直走。
- **纠偏 / 回线**：保留 Planning 规划器的 Frenet 横向候选；兜底的 A* 改成代价感知（可通行代价 + 偏离示教线代价），与 Nav2 Smac Hybrid-A*、ETH art_planner 的思路一致。锐利台阶的立面格不再判为"未知 = 障碍"，而是带高度的"台阶边"格，由当前 policy 的能力决定能否通过。
- **跟线**：Regulated Pure Pursuit（按曲率和离障碍的距离调速），加最低速度约束（J3100 在非平地 ≥ 0.5 m/s，否则会卡在小坎上）。
- **切换 policy**：路线标注只给出"允许开始切换的区间"。真正切换由 Router 的 ALIGN 门在感知条件同时满足并保持 0.4 s 时触发：
  - 距实测台阶边 0.45–0.70 m；
  - 对实测法线的航向误差 ≤ 6°；
  - 横摆角速度 ≤ 0.1 rad/s；
  - 速度 ≤ 0.3 m/s。

  这和"检测到台阶地形进入台阶模式、通过后切回"的做法一致。
- **1150 爬升时的控制**：航向保持在实测法线 ±12° 内（它几乎不会转向）；横向只通过小角度航向偏置修正，偏置由左右落差的居中量给出；按实测前进速度压指令，因为它会超速。
- **确认通过（VERIFY_CLEAR）**：高度网格显示机身下和前方 0.3 m 没有台阶边、后轮已过最后一道边 0.6 m、俯仰 < 5°，持续 0.4 s。任何一项拿不到就判失败（fail closed）。
- **错过 WP**：1150 越过未到达的 WP 就停下，切回 J3100 原地转向补点。

### 5. 修改清单

### 6. 验收指标

- 仿真：每段 10 个随机种子成功率 ≥ 90%；定位偏置 0.2 m / 3° 下成功率下降不超过 10 个百分点；零摔倒；急停线（45 / 12 N·m、25.8 / 30 rad/s）越线时间计入报告。
- 真机：按 native 计划，每段连续两次通过再串联；人工接管、急停、失败分别记录，不计为成功。

### 2. 接入新 SLAM 的验证步骤

1. **建图大圈**（第 5.2 节），保存 x_nav 地图，同时录原始传感器数据包。
2. **定位质量：**

   | 检查项 | 通过标准 |
   |---|---|
   | 静止 60 s | 漂移 < 1 cm |
   | 平地上横滚、俯仰 | ≈ 0（说明 IMU 外参正确） |
   | 回到起点 | 首尾误差 < 10 cm |
   | 在 WP01 重定位 | 每次都能成功 |
   | 位姿频率 | ≥ 10 Hz |

3. **配准到 v3**（第 6 节）：按区域看残差，各处 < 0.1 m 才用一个刚体变换。
4. **位姿转发节点：** 转成 v3 坐标系后发布为 ROS 2 `/localization/odom`，同时修正高度基准。`rl_nav` 默认“机身 = 地面 + 0.42 m”，x_nav 配置里是 0.27，要在平地实测。
5. **叠图检查：** 用“x_nav 位姿 + 变换”把实时激光投到 v3 点云上，墙面、台阶边应在约 5 cm 以内。
6. **影子运行：** 运行 `rl_nav`，但 SDK runner 不接管，用遥控器带着走全程。检查 `/rl_nav/status` 的进度、到点顺序、步行↔台阶切换位置。

### 3. 现有 app（手机现场助手 `/field`）能不能做：核对结果

现场助手是 `s10-field-assistant/tools/s10_mapping_web`：AGX 上的网页，加 106 上的 worker。逐项对照新流程：

| 新流程需要 | 现有 app | 结论 |
|---|---|---|
| 读取 x_nav 位姿 | 只读 106 官方定位 `/ODOM`（`field_robot.py:35`） | **做不到**：x_nav 是 AGX 上的 ROS 1，app 看不到 |
| 标 WP | 有：停稳后 3 s 采样取平均，带稳定性检查 | 可用思路；但要改数据源 |
| 标切换点、楼梯段 | 标点的 `segment` 只允许 `flat`，写明“首版仅标记平地短段”（`field_core.py:89`） | **做不到** |
| 连续录示教路径 | 只有 10–30 s 原始录制（`field_core.py:84`），总预算 512 MiB，录在 106 上 | **做不到** |
| 航点编号 | 名称自由填写，没有 WP01–WP30 固定清单 | **易出错**：照片顺序与正式顺序相反，已经踩过坑 |
| 精度门限 | 静止离散 ≤ 0.10 m / 5°（`field_core.py:210`），> 3 cm 只提示 | **太松**：精确 WP 需要 ≤ 2 cm / 1° |
| 高度 | z 是定位参考点高度，不是地面 | 需要离线换算成地面高度 |
| 输出 | `waypoints-review.json`，永远 `navigation_ready:false`，不是 route_v2 格式 | 需要转换工具 |
| 复测重复性 | 有（⑤B 航点返回复测，水平/高度/朝向差） | **好用**：新工具保留这个思路 |

**额外风险（漏洞）：**

1. **“加载地图”会改整机状态。** 按钮调用官方 `drmap map activate`（`field_robot.py:436`），会切换整机的激活地图并重启官方定位。新狗是和别人共用的，不能再按这个按钮。
2. **设备绑定 48 号。** 身份校验认 48 号 106 的 `machine-id` 哈希（`field_robot.py:302`），后台 SSH 固定了 48 号 106 的主机密钥，入口靠 48 号 103 上的端口转发。
   - **主机密钥拦不住：** 050 号的 103 / 106 与 48 号主机密钥相同（厂商镜像）。新狗上靠专用密钥没装来保证连不上：09-19 已实测，该密钥被 050 号的 106 拒绝。
   - 手机入口 `10.21.41.1:8080` 在新狗上也不存在。
   - 要在新狗上用，就得在新狗的 103/106 上重新部署，属于厂商板系统改动，需另行确认。
3. **数据存在 106 上**（SQLite 和录制文件）。换狗后留在旧狗；新流程的数据应存在我们自己的 AGX 上。

**结论：** 旧现场助手只能在旧狗、官方定位、v3 地图下标平地草稿点，不支持新流程。

#### 5.0 准备（每次上场前）

- **人员：** 一人拿遥控器负责运动和急停，一人拿电脑记录。全程只用遥控器行走：`rl_nav`、`s10_ros1_control`、x_nav 的 planner / w_nav 都不开。
- **现场标记：** 在 WP01（门口）地面用胶带贴一个“脚印框”：前两脚位置加朝向箭头。每次建图、每次定位都从这里、这个朝向出发。

  ```bash
  source ~/ros1_gateway/ros1/ros1_env.sh
  export ROS_MASTER_URI=http://127.0.0.1:11311 ROS_IP=127.0.0.1
  ```

- **检查数据链路**（网关和 x_nav 由负责人启动）：

  ```bash
  rostopic hz /LIDAR/POINTS /IMU
  ```

  应约 10 Hz / 200 Hz。再确认 x_nav 的位姿话题。新狗实测为 `/base_link/odom`（10 Hz）：

#### 5.1 标记命令（所有记录共用）

在第二个终端里用下面这条命令打标记，引号里换成标记名：

```bash
rostopic pub -1 /teach/mark std_msgs/String "data: 'WP05'"
```

| 标记名 | 什么时候打 |
|---|---|
| `WP01` … `WP30` | 机器人停在该红点上、静止后打。**编号按正式顺序：WP01 = 门口 Start，WP30 = 远端高处**（与照片顺序相反） |
| `SWIN` | 停在“该交给台阶 policy”的位置后打 |
| `SWOUT` | 停在“可以交还步行 policy”的位置后打 |
| `PATH_START` / `PATH_END` | 示教路径的开始 / 结束 |
| `REDO` | 上一个标记作废（位置没停好、编号打错时用），然后重新标 |
| `NOTE:文字` | 任何现场说明，例如 `NOTE:WP16两面旗取左边那面` |

打标记前后都要保持机器人静止至少 3 s。离线工具只取标记前后 3 s 的位姿平均，并检查离散度（≤ 2 cm / 1°，超了会被标为不合格）。

#### 5.2 第一步：建图大圈（带回环）

**需要重新录吗？需要。** 原因：

- x_nav 必须用自己的地图定位。
- 赛道是一条长线（门口→B 楼梯→……→远端），只走单程，远端误差会越积越大。
- **往返走**能在整条路线上反复看到同一处，起终点也重合，回环修正最充分。
- 回环好的地图也最容易和 v3 做刚体配准。

步骤：

1. 机器人放在 WP01 的脚印框里，按厂商说明启动 x_nav 建图。**同时**开始录原始数据：

   ```bash
   mkdir -p ~/teach && cd ~/teach && rosbag record -O mapping_loop_$(date +%Y%m%d_%H%M).bag /LIDAR/POINTS /IMU $POSE
   ```

2. 先原地静止 5 s，再用遥控器沿赛道慢速走到 WP30：平地 0.3–0.5 m/s，楼梯按平时安全速度。
   - 转弯慢一点，不要原地快速打转。
   - 尽量避开人群，走动的人会让地图出重影。
3. 在 WP30 附近掉头，**沿原路走回 WP01**，最后停回脚印框（位置和朝向都要对上），静止 5 s。
4. 按厂商说明保存地图，**记下地图名**。然后在录制终端按 Ctrl+C 停止录制。
5. 立即检查：
   - 厂商界面或日志里有回环记录。
   - 地图里墙面、台阶没有双影。
   - 起点处首尾位姿差 < 10 cm。
   - 不合格就重走，不要带着有问题的地图往下做。

#### 5.3 第二步：切到定位模式，录 WP

1. 按厂商说明加载刚保存的地图、进入**定位模式**。机器人从 WP01 脚印框出发，确认重定位成功：静止时 `POSE` 稳定、不跳变。
2. 开始录（位姿数据很小，一个 bag 可以录一整天）：

   ```bash
   cd ~/teach && rosbag record -O session_wp_$(date +%Y%m%d_%H%M).bag $POSE /teach/mark /IMU
   ```

3. 按正式顺序 WP01→WP30 逐个走过去。每个红点：
   - **位置：** 机身中心对准红点。对不准时以机身中心为准，不以某只脚为准。
   - **朝向：** 朝向下一个 WP。
   - **静止 3 s** → 打 `WPxx` → 再静止 3 s → 离开。
   - 红点在台阶或岩脊上、机器人不能安全停上去时，停在最近的安全位置，打 `WPxx`，再补一条 `NOTE:WPxx未能站上红点，偏差约xx cm朝xx方向`。
4. **先重点测低置信度的点：** WP16（两面旗，用 `NOTE` 说明取哪面）、WP24、WP25、WP27、WP28、WP30，以及 WP06、WP07（B 楼梯上，仿真里曾挪过约 0.6 m）。
5. **复测：** 全部标完后，回到 WP01、WP10、WP20 各再标一次（同样打 `WPxx`，离线会识别为复测）。前后相差应 < 10 cm；超了说明定位或停靠有问题，要找原因。

#### 5.4 第三步：录切换点

在同一个录制里（或单独开一个 bag）做。每个需要台阶 policy 的地方要标**一对**：

- **`SWIN`（交给台阶 policy）：**
  - 停在第一级台阶或坎**前 0.3–0.5 m** 的平地上。
  - **机身正对台阶边**（垂直于台阶边，不要斜着对）。
  - 静止 3 s，打 `SWIN`。
  - 原因：步行→台阶是行进中接管，到第一级之前必须已经切完、方向摆正。
- **`SWOUT`（交还步行 policy）：**
  - 停在最后一级之后、**离边缘 ≥ 0.5 m 的稳定平地**上。
  - 静止 3 s，打 `SWOUT`。
  - 原因：台阶→步行交还时有 0.25 s 的安全保持（SafeHold），不能在坡上或边缘交还，否则会滑。

已知需要成对标记的地方（与 route_v2 的 stairs 段对应）：B 楼梯及其中间平台、WP03→WP04 小台阶、石笼坎、人工台/黄色凸台、乱石溪床。**余量最小的几处要特别仔细**：WP11 岩脊、WP14 的 0.19 m 坎、B 楼梯第一级（原路线约 50° 斜穿，这次尽量正对）。

#### 5.5 第四步：录最短手动路径（示教）

这条路径会成为 route_v2 每段的中心线。“最短”指**在 policy 能力范围内最短**，不是抄近路。

1. 从 WP01 脚印框出发，开始录：

   ```bash
   cd ~/teach && rosbag record -O session_path_$(date +%Y%m%d_%H%M).bag $POSE /teach/mark /IMU
   ```

2. 打 `PATH_START`，然后**连续**走完 WP01→WP30：经过每个红点，中途不用停；想顺便记时间可以短停再打 `WPxx`。到 WP30 打 `PATH_END`。
3. 走线规则（来自两个 policy 的实测能力）：

   | 场景 | 规则 |
   |---|---|
   | 平地 | 尽量走直线；开阔平地可以切弯，但离边缘、障碍保持 ≥ 0.5 m |
   | 进台阶前 | 留 ≥ 1 m 的直线助跑，**垂直**正对台阶边；不要贴着台阶侧边走 |
   | 台阶上 | 不转弯（1150 几乎不能转，左转有翻倒风险）；走台阶中间 |
   | 坡 | 避开 > 6° 的侧坡（步行 policy 会往下滑） |
   | 台阶高度 | 不走 > 18 cm 的台阶（1150 在 21 cm 会摔） |
   | 落差 | 离落差 ≥ 0.4 m |
   | 低矮树冠（WP29 附近） | 选机身能完全通过的位置 |

4. 速度保持稳定：平地约 0.3 m/s，台阶按安全速度。
5. **最好完整走两遍。** 离线比较两遍，选更短且更平顺的那条，并用第二遍检查路线的可重复性。

#### 5.6 数据交回

所有 bag 都在 AGX 的 `~/teach/` 下。当天结束时把文件名、地图名、每次的说明（哪些 WP 没站上、哪些 `REDO` 过）记在同目录的 `README.txt`。**不要删除或覆盖任何 bag。** 传到电脑后逐个核对大小和 SHA256。

### 6. 离线处理（我们来做）

1. **提取：** 从 bag 里取每个标记前后 3 s 的位姿平均和离散度，生成 WP、切换点和示教路径表。
   - 检查编号是否齐全、是否重复，处理作废（页面的 `VOID`、命令行的 `REDO`），计算复测差。
   - 地面高度 = 机身高度 − 实测机身偏置。
2. **地图配准（x_nav 地图 → v3 点云）：**
   - 用 WP01 的位置朝向或 3 处以上明显地标（门框、楼梯角）给初值，再做点到面 ICP（由粗到细）。
   - **按区域输出残差**（门口、B 楼梯、中段、远端）。
   - 各处 < 0.1 m：保持 v3 为参考，用一个刚体变换。
   - 残差沿路线变大：改用 x_nav 地图作参考，用它的点云重建 `course_terrain` / `map_surface`，重新做路线准备和仿真。
3. **生成 route_v2（FIELD 版）：**
   - WP 用实测值，同时保存 x_nav 原始坐标。
   - 中心线用示教路径，按到达每个 WP 的时刻切段。
   - 每段步态：包含 SWIN…SWOUT 的段用 `stairs`，其余 `flat`。
   - 附一张新旧 WP 对照表：移动量超过原不确定半径的逐个说明。
4. **路线准备与仿真：**

   ```bash
   ros2 run s10_auto_nav rl_nav_prepare --route route_v2_field.json --terrain course_terrain.npz \
     --overrides overrides_v1.json --method first --out prepared/
   ```

   - 旧的 `overrides_v1.json` 是按旧中心线做的。新示教线与旧线差别不大的段保留；差别大的段用新线，并在报告里说明。
   - `prepare_report.json` 里不能有穿过未知地面或落差的地方。
   - SWIN/SWOUT 与自动标注的台阶区逐个对照：相差 > 0.5 m 的要查原因。
   - MuJoCo 全程加分段，多个随机种子，并加入 0.2 m / 3° 的定位偏置。和 30/30、713 s 的基线比较停车、掉头、用时、保护线越界。每段成功率目标 ≥ 90%。
5. **冻结并部署：** 路线版本记录哈希，把 `prepared/` 部署到 AGX。

### 7. 其他要做的事

#### 7.1 厂商（x_nav）需要确认

- **S10 的外参：** `extrinsic_T` 还是 MID-360 默认值，而 106 官方 SLAM 的雷达、IMU 外参都是单位阵。
- **点云格式：** `lidar_type: 7` 是否读取我们的 `ring` 和逐点 `timestamp` 字段。
- **建图与定位操作：** 怎么开始/保存建图、怎么进入只定位模式（不输出 `/cmd_vel`）、怎么设初始位姿。
- **位姿话题：** 已确认 `/base_link/odom`（10 Hz）；还要确认它对应机身哪个点。
- **`map_manager`：** 镜像里仍缺；手册中导航点、虚拟障碍物的保存可能依赖它。建图本身已能运行（地图“111”，授权通过）。
- **地图导出：** 地图点云文件在哪里（我们要拿去和 v3 配准）。
- **厂商网页：** 是否自带标点 / 录路径功能；有的话可以一起用，但仍要按第 5 节录一份我们自己的数据。
- **授权与版本：** 授权能否在 eMMC 上生效；`nav:3.2.1.arm.beta` 是否稳定。

#### 7.2 安全

- **速度只能有一个来源。** 导航时 `rl_nav` 独占 `/cmd_vel`：不要运行 `s10_ros1_control`，也不要运行 x_nav 的 `w_nav`。
- 我们的 ROS 1 网关是单向的，ROS 1 的 `/cmd_vel` 进不了 ROS 2。
- 录数据时只用遥控器驱动。
- 共用机器人上不要按旧现场助手的“加载地图”，也不要改官方激活地图。

#### 7.3 AGX 算力与存储

- x_nav、网关、感知、`rl_nav`、policy 推理共用 8 个核：限制 x_nav 的核数（配置里 `numberOfCores: 8`），并实测负载。
- 原始数据包很大：建图大圈录完尽快拷走。

#### 7.4 感知输入

- `rl_nav` 的恢复层需要 AGX 上 ROS 2 的 `/perception/points_yaw` 和高度网格。
- AGX 自己的合并点云应该够用，但要对照仿真里的感知合同核对一次。
