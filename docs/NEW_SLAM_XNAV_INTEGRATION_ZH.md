# 新 SLAM（x_nav）接入我们的导航策略：航点实测、切换点、示教路线与地图对齐

2026-09-19。本文是计划与现场操作说明，尚未执行。适用于：厂商 x_nav（ROS 1，AGX 上的 Docker 容器）作为新的 SLAM/定位，我们的 `rl_nav` 跟随器 + J3100 步行 / 1150 台阶 policy 负责导航与运动。

## 结论先说

1. **要重新走一圈带回环的大圈建图。** x_nav 只能在自己建的地图里定位；回环保证远端不漂。走法见第 5.2 节。
2. **旧航点不做“对齐”，而是全部现场重测。** 旧的 30 个 WP 是用照片时间戳推算的（启发式匹配），误差半径 1.5–3 m，只能当粗检参考。
3. **v3 继续作为参考坐标系。** x_nav 新地图与 v3 点云做一次配准，得到一个坐标变换。已验证的路线处理、台阶区和仿真不用重做。
4. **旧手机现场助手做不了新流程**（只认官方定位、只能标平地点、不能连续录路径，见第 3 节），**已新做“采集助手”页面 `/teach`**：建图采集、标 WP / 切换点、示教路径三件事都在上面，数据存在 AGX。
   - 已部署到 AGX。新狗（050 号）上后台已接通 x_nav 位姿、点云、IMU；手机访问待验证。
   - 队友操作说明：`s10-field-assistant/tools/s10_mapping_web/TEACH_GUIDE_ZH.md`。

## 1. 依据（调研结论）

- **已验证的所有东西都在 v3 的 `map` 坐标系里**（106 官方 SLAM 地图 `0914_fr_v3-20260914-142008`）：
  - `tools/wp_match/out/route_v2.json`：30 个 WP、示教中心线、每段步态与限速。
  - `rl_nav_prepare` 的输入输出：`course_terrain.npz`（由 v3 点云生成）、`map_surface.npz`、`overrides_v1.json`（9 段人工修正）、16 个台阶区（maneuvers）。
  - MuJoCo 全场场景：全程 30/30、713 s 的那一版（`S10_Nav_FullV3_Repro_20260919`）。
- **x_nav 只能在它自己建的地图里定位。** 原点和朝向取决于建图起点，坐标和 v3 对不上。
- **`rl_nav` 对定位只要求一样东西：** `odom` 话题上的 map 坐标系 `nav_msgs/Odometry`（`-r odom:=/localization/odom`）。
  - 它按**收到消息的时间**判断位姿是否过期，不看消息头时间戳，所以 AGX 与机器人的时钟差不影响它（新狗上 AGX 已改为 PTP 跟随 103）。
- **旧 WP 的来源：** 拍照时间插值到 v3 建图关键帧，再取机器人脚下地面高度（`tools/wp_match/README_ZH.md`）。
  - 手机与机器人时钟偏差没有校验过，照片里机器人和红点之间也有距离。
  - 所以置信度只有 high 1.5 m / medium 2–3 m / low 3 m，WP16/24/25/27/28/30 照片里甚至没拍到机器人。

接法：**把 x_nav 的位姿变换到 v3 坐标系**，跟随器、路线、台阶区和仿真一律不动。

```text
/LIDAR/POINTS、/IMU ─► ROS 1 网关 ─► x_nav（只做 SLAM + 定位：planner 和 w_nav 关闭）
                                          │ x_nav 坐标系下的位姿
                                          ▼
                     位姿转发节点（新增）：乘 T(v3←x_nav) ─► ROS 2 /localization/odom（v3 坐标系）
                                          ▼
                     rl_nav（不改）─► /cmd_vel + /strategy/joint_owner ─► SDK：J3100 步行 / 1150 台阶
```

## 2. 接入新 SLAM 的验证步骤

1. **建图大圈**（第 5.2 节），保存 x_nav 地图，同时录原始传感器数据包。
2. **定位质量：**

   | 检查项 | 通过标准 |
   |---|---|
   | 静止 60 s | 漂移 < 1 cm |
   | 平地上横滚、俯仰 | ≈ 0（说明 IMU 外参正确） |
   | 回到起点 | 首尾误差 < 10 cm |
   | 在 WP01 重定位 | 每次都能成功 |
   | 位姿频率 | ≥ 10 Hz |

3. **配准到 v3**（第 6 节）：按区域看残差，各处 < 0.1 m 才用一个刚体变换。
4. **位姿转发节点：** 转成 v3 坐标系后发布为 ROS 2 `/localization/odom`，同时修正高度基准。`rl_nav` 默认“机身 = 地面 + 0.42 m”，x_nav 配置里是 0.27，要在平地实测。
5. **叠图检查：** 用“x_nav 位姿 + 变换”把实时激光投到 v3 点云上，墙面、台阶边应在约 5 cm 以内。
6. **影子运行：** 运行 `rl_nav`，但 SDK runner 不接管，用遥控器带着走全程。检查 `/rl_nav/status` 的进度、到点顺序、步行↔台阶切换位置。

## 3. 现有 app（手机现场助手 `/field`）能不能做：核对结果

现场助手是 `s10-field-assistant/tools/s10_mapping_web`：AGX 上的网页，加 106 上的 worker。逐项对照新流程：

| 新流程需要 | 现有 app | 结论 |
|---|---|---|
| 读取 x_nav 位姿 | 只读 106 官方定位 `/ODOM`（`field_robot.py:35`） | **做不到**：x_nav 是 AGX 上的 ROS 1，app 看不到 |
| 标 WP | 有：停稳后 3 s 采样取平均，带稳定性检查 | 可用思路；但要改数据源 |
| 标切换点、楼梯段 | 标点的 `segment` 只允许 `flat`，写明“首版仅标记平地短段”（`field_core.py:89`） | **做不到** |
| 连续录示教路径 | 只有 10–30 s 原始录制（`field_core.py:84`），总预算 512 MiB，录在 106 上 | **做不到** |
| 航点编号 | 名称自由填写，没有 WP01–WP30 固定清单 | **易出错**：照片顺序与正式顺序相反，已经踩过坑 |
| 精度门限 | 静止离散 ≤ 0.10 m / 5°（`field_core.py:210`），> 3 cm 只提示 | **太松**：精确 WP 需要 ≤ 2 cm / 1° |
| 高度 | z 是定位参考点高度，不是地面 | 需要离线换算成地面高度 |
| 输出 | `waypoints-review.json`，永远 `navigation_ready:false`，不是 route_v2 格式 | 需要转换工具 |
| 复测重复性 | 有（⑤B 航点返回复测，水平/高度/朝向差） | **好用**：新工具保留这个思路 |

**额外风险（漏洞）：**

1. **“加载地图”会改整机状态。** 按钮调用官方 `drmap map activate`（`field_robot.py:436`），会切换整机的激活地图并重启官方定位。新狗是和别人共用的，不能再按这个按钮。
2. **设备绑定 48 号。** 身份校验认 48 号 106 的 `machine-id` 哈希（`field_robot.py:302`），后台 SSH 固定了 48 号 106 的主机密钥，入口靠 48 号 103 上的端口转发。
   - **主机密钥拦不住：** 050 号的 103 / 106 与 48 号主机密钥相同（厂商镜像）。新狗上靠我们的专用密钥和 106 后台都没装来保证连不上，未实测。
   - 手机入口 `10.21.41.1:8080` 在新狗上也不存在。
   - 要在新狗上用，就得在新狗的 103/106 上重新部署，属于厂商板系统改动，需另行确认。
3. **数据存在 106 上**（SQLite 和录制文件）。换狗后留在旧狗；新流程的数据应存在我们自己的 AGX 上。

**结论：** 旧现场助手只能在旧狗、官方定位、v3 地图下标平地草稿点，不支持新流程。

### 3.1 新页面“采集助手”`/teach` 如何逐项解决

| 漏洞 | 采集助手的做法 |
|---|---|
| 读不到 x_nav 位姿 | 后台在 AGX 的 ROS 1 环境里直接订阅 x_nav 位姿，支持 `Odometry` / `PoseStamped` / `PoseWithCovarianceStamped`，话题名可配置 |
| 只能标平地点 | 有 WP01–WP30 方格、▲SWIN / ▼SWOUT 切换点按钮，并自动配对 |
| 不能连续录路径 | 三种录制：建图采集（点云 + IMU + 位姿，大包自动分文件）、标点、示教；另存轻量轨迹 CSV |
| 编号易错 | 固定 30 个编号按钮，合格后自动跳到下一个；页面写明正式顺序 |
| 门限太松 | 3 秒采样，≤ 2 cm / 1° 才合格，并写明不合格原因 |
| “加载地图”会改整机状态 | 没有任何切图、控制按钮；不调用官方 drmap，不连 106 |
| 设备绑定 48 号、数据存 106 | 只依赖 AGX；数据存 AGX `~/teach/sessions/`；手机直接访问 AGX |
| 复测 | 同一个 WP 可以重复标，全部保留；离线计算前后差 |
| 回环 | 建图时实时显示“距起点”，并在地图上标出起点 |

实现、测试与回滚见 `TEACH_GUIDE_ZH.md` 第 10 节。第 5 节的命令行方法保留为备用。

## 4. 各类数据之间的关系

| 名称 | 是什么 | 怎么得到 | 用在哪 |
|---|---|---|---|
| WP | 赛道上的红点（正式 30 个） | 机器人停在红点上，静止 3 s 取平均 | route_v2 的 `waypoints` |
| 切换点 SWIN / SWOUT | 步行→台阶 policy 的接管点 / 台阶→步行的交还点 | 机器人停在该位置标记 | 核对与修正台阶区（maneuvers） |
| 示教路径 | 希望 policy 走的线，尽量短但必须安全 | 遥控器连续走一遍，录位姿 | route_v2 每段的 `centerline` |
| 建图大圈 | x_nav 地图 | 回环建图 | 定位，以及与 v3 配准 |

**关键顺序：WP、切换点和示教路径必须在“定位模式 + 已保存的最终地图”下录，不能在建图过程中录。** 建图时回环会把之前的位姿整体修正，边建边录的坐标之后会对不上。

## 5. 给队友的现场操作说明

**首选用采集助手页面**，按 `TEACH_GUIDE_ZH.md` 操作：页面上的步骤和本节一致，标点结果当场显示合格与否。页面打不开或后台出问题时，用本节的命令行方法作为**备用**。两种方式的标记都写在 `/teach/mark` 话题上（页面写 JSON 并附当场的合格结果，命令行写纯文本），离线处理时一起提取。

### 5.0 准备（每次上场前）

- **人员：** 一人拿遥控器负责运动和急停，一人拿电脑记录。全程只用遥控器行走：`rl_nav`、`s10_ros1_control`、x_nav 的 planner / w_nav 都不开。
- **现场标记：** 在 WP01（门口）地面用胶带贴一个“脚印框”：前两脚位置加朝向箭头。每次建图、每次定位都从这里、这个朝向出发。
- **登录 AGX**（现场连机器人 Wi-Fi 用 `ssh golai@10.21.33.102`，远程用 `ssh s10-48-remote`），打开两个终端，都先执行：

  ```bash
  source ~/ros1_gateway/ros1/ros1_env.sh
  export ROS_MASTER_URI=http://127.0.0.1:11311 ROS_IP=127.0.0.1
  ```

- **检查数据链路**（网关和 x_nav 由负责人启动）：

  ```bash
  rostopic hz /LIDAR/POINTS /IMU
  ```

  应约 10 Hz / 200 Hz。再确认 x_nav 的位姿话题。新狗实测为 `/base_link/odom`（10 Hz）：

  ```bash
  rostopic list | grep -i -E "odom|pose"
  ```

  下文用 `POSE` 代指这个话题，先设一次：

  ```bash
  export POSE=/base_link/odom
  ```

- **磁盘：** 建图大圈要录原始数据，约 1.5 GB/分钟。先确认剩余空间足够，一般走 15 分钟要留 25 GB 以上：

  ```bash
  df -h ~
  ```

### 5.1 标记命令（所有记录共用）

在第二个终端里用下面这条命令打标记，引号里换成标记名：

```bash
rostopic pub -1 /teach/mark std_msgs/String "data: 'WP05'"
```

| 标记名 | 什么时候打 |
|---|---|
| `WP01` … `WP30` | 机器人停在该红点上、静止后打。**编号按正式顺序：WP01 = 门口 Start，WP30 = 远端高处**（与照片顺序相反） |
| `SWIN` | 停在“该交给台阶 policy”的位置后打 |
| `SWOUT` | 停在“可以交还步行 policy”的位置后打 |
| `PATH_START` / `PATH_END` | 示教路径的开始 / 结束 |
| `REDO` | 上一个标记作废（位置没停好、编号打错时用），然后重新标 |
| `NOTE:文字` | 任何现场说明，例如 `NOTE:WP16两面旗取左边那面` |

打标记前后都要保持机器人静止至少 3 s。离线工具只取标记前后 3 s 的位姿平均，并检查离散度（≤ 2 cm / 1°，超了会被标为不合格）。

### 5.2 第一步：建图大圈（带回环）

**需要重新录吗？需要。** 原因：

- x_nav 必须用自己的地图定位。
- 赛道是一条长线（门口→B 楼梯→……→远端），只走单程，远端误差会越积越大。
- **往返走**能在整条路线上反复看到同一处，起终点也重合，回环修正最充分。
- 回环好的地图也最容易和 v3 做刚体配准。

步骤：

1. 机器人放在 WP01 的脚印框里，按厂商说明启动 x_nav 建图。**同时**开始录原始数据：

   ```bash
   mkdir -p ~/teach && cd ~/teach && rosbag record -O mapping_loop_$(date +%Y%m%d_%H%M).bag /LIDAR/POINTS /IMU $POSE
   ```

2. 先原地静止 5 s，再用遥控器沿赛道慢速走到 WP30：平地 0.3–0.5 m/s，楼梯按平时安全速度。
   - 转弯慢一点，不要原地快速打转。
   - 尽量避开人群，走动的人会让地图出重影。
3. 在 WP30 附近掉头，**沿原路走回 WP01**，最后停回脚印框（位置和朝向都要对上），静止 5 s。
4. 按厂商说明保存地图，**记下地图名**。然后在录制终端按 Ctrl+C 停止录制。
5. 立即检查：
   - 厂商界面或日志里有回环记录。
   - 地图里墙面、台阶没有双影。
   - 起点处首尾位姿差 < 10 cm。
   - 不合格就重走，不要带着有问题的地图往下做。

### 5.3 第二步：切到定位模式，录 WP

1. 按厂商说明加载刚保存的地图、进入**定位模式**。机器人从 WP01 脚印框出发，确认重定位成功：静止时 `POSE` 稳定、不跳变。
2. 开始录（位姿数据很小，一个 bag 可以录一整天）：

   ```bash
   cd ~/teach && rosbag record -O session_wp_$(date +%Y%m%d_%H%M).bag $POSE /teach/mark /IMU
   ```

3. 按正式顺序 WP01→WP30 逐个走过去。每个红点：
   - **位置：** 机身中心对准红点。对不准时以机身中心为准，不以某只脚为准。
   - **朝向：** 朝向下一个 WP。
   - **静止 3 s** → 打 `WPxx` → 再静止 3 s → 离开。
   - 红点在台阶或岩脊上、机器人不能安全停上去时，停在最近的安全位置，打 `WPxx`，再补一条 `NOTE:WPxx未能站上红点，偏差约xx cm朝xx方向`。
4. **先重点测低置信度的点：** WP16（两面旗，用 `NOTE` 说明取哪面）、WP24、WP25、WP27、WP28、WP30，以及 WP06、WP07（B 楼梯上，仿真里曾挪过约 0.6 m）。
5. **复测：** 全部标完后，回到 WP01、WP10、WP20 各再标一次（同样打 `WPxx`，离线会识别为复测）。前后相差应 < 10 cm；超了说明定位或停靠有问题，要找原因。

### 5.4 第三步：录切换点

在同一个录制里（或单独开一个 bag）做。每个需要台阶 policy 的地方要标**一对**：

- **`SWIN`（交给台阶 policy）：**
  - 停在第一级台阶或坎**前 0.3–0.5 m** 的平地上。
  - **机身正对台阶边**（垂直于台阶边，不要斜着对）。
  - 静止 3 s，打 `SWIN`。
  - 原因：步行→台阶是行进中接管，到第一级之前必须已经切完、方向摆正。
- **`SWOUT`（交还步行 policy）：**
  - 停在最后一级之后、**离边缘 ≥ 0.5 m 的稳定平地**上。
  - 静止 3 s，打 `SWOUT`。
  - 原因：台阶→步行交还时有 0.25 s 的安全保持（SafeHold），不能在坡上或边缘交还，否则会滑。

已知需要成对标记的地方（与 route_v2 的 stairs 段对应）：B 楼梯及其中间平台、WP03→WP04 小台阶、石笼坎、人工台/黄色凸台、乱石溪床。**余量最小的几处要特别仔细**：WP11 岩脊、WP14 的 0.19 m 坎、B 楼梯第一级（原路线约 50° 斜穿，这次尽量正对）。

### 5.5 第四步：录最短手动路径（示教）

这条路径会成为 route_v2 每段的中心线。“最短”指**在 policy 能力范围内最短**，不是抄近路。

1. 从 WP01 脚印框出发，开始录：

   ```bash
   cd ~/teach && rosbag record -O session_path_$(date +%Y%m%d_%H%M).bag $POSE /teach/mark /IMU
   ```

2. 打 `PATH_START`，然后**连续**走完 WP01→WP30：经过每个红点，中途不用停；想顺便记时间可以短停再打 `WPxx`。到 WP30 打 `PATH_END`。
3. 走线规则（来自两个 policy 的实测能力）：

   | 场景 | 规则 |
   |---|---|
   | 平地 | 尽量走直线；开阔平地可以切弯，但离边缘、障碍保持 ≥ 0.5 m |
   | 进台阶前 | 留 ≥ 1 m 的直线助跑，**垂直**正对台阶边；不要贴着台阶侧边走 |
   | 台阶上 | 不转弯（1150 几乎不能转，左转有翻倒风险）；走台阶中间 |
   | 坡 | 避开 > 6° 的侧坡（步行 policy 会往下滑） |
   | 台阶高度 | 不走 > 18 cm 的台阶（1150 在 21 cm 会摔） |
   | 落差 | 离落差 ≥ 0.4 m |
   | 低矮树冠（WP29 附近） | 选机身能完全通过的位置 |

4. 速度保持稳定：平地约 0.3 m/s，台阶按安全速度。
5. **最好完整走两遍。** 离线比较两遍，选更短且更平顺的那条，并用第二遍检查路线的可重复性。

### 5.6 数据交回

所有 bag 都在 AGX 的 `~/teach/` 下。当天结束时把文件名、地图名、每次的说明（哪些 WP 没站上、哪些 `REDO` 过）记在同目录的 `README.txt`。**不要删除或覆盖任何 bag。** 传到电脑后逐个核对大小和 SHA256。

## 6. 离线处理（我们来做）

1. **提取：** 从 bag 里取每个标记前后 3 s 的位姿平均和离散度，生成 WP、切换点和示教路径表。
   - 检查编号是否齐全、是否重复，处理作废（页面的 `VOID`、命令行的 `REDO`），计算复测差。
   - 地面高度 = 机身高度 − 实测机身偏置。
2. **地图配准（x_nav 地图 → v3 点云）：**
   - 用 WP01 的位置朝向或 3 处以上明显地标（门框、楼梯角）给初值，再做点到面 ICP（由粗到细）。
   - **按区域输出残差**（门口、B 楼梯、中段、远端）。
   - 各处 < 0.1 m：保持 v3 为参考，用一个刚体变换。
   - 残差沿路线变大：改用 x_nav 地图作参考，用它的点云重建 `course_terrain` / `map_surface`，重新做路线准备和仿真。
3. **生成 route_v2（FIELD 版）：**
   - WP 用实测值，同时保存 x_nav 原始坐标。
   - 中心线用示教路径，按到达每个 WP 的时刻切段。
   - 每段步态：包含 SWIN…SWOUT 的段用 `stairs`，其余 `flat`。
   - 附一张新旧 WP 对照表：移动量超过原不确定半径的逐个说明。
4. **路线准备与仿真：**

   ```bash
   ros2 run s10_auto_nav rl_nav_prepare --route route_v2_field.json --terrain course_terrain.npz \
     --overrides overrides_v1.json --method first --out prepared/
   ```

   - 旧的 `overrides_v1.json` 是按旧中心线做的。新示教线与旧线差别不大的段保留；差别大的段用新线，并在报告里说明。
   - `prepare_report.json` 里不能有穿过未知地面或落差的地方。
   - SWIN/SWOUT 与自动标注的台阶区逐个对照：相差 > 0.5 m 的要查原因。
   - MuJoCo 全程加分段，多个随机种子，并加入 0.2 m / 3° 的定位偏置。和 30/30、713 s 的基线比较停车、掉头、用时、保护线越界。每段成功率目标 ≥ 90%。
5. **冻结并部署：** 路线版本记录哈希，把 `prepared/` 部署到 AGX。

## 7. 其他要做的事

### 7.1 厂商（x_nav）需要确认

- **S10 的外参：** `extrinsic_T` 还是 MID-360 默认值，而 106 官方 SLAM 的雷达、IMU 外参都是单位阵。
- **点云格式：** `lidar_type: 7` 是否读取我们的 `ring` 和逐点 `timestamp` 字段。
- **建图与定位操作：** 怎么开始/保存建图、怎么进入只定位模式（不输出 `/cmd_vel`）、怎么设初始位姿。
- **位姿话题：** 已确认 `/base_link/odom`（10 Hz）；还要确认它对应机身哪个点。
- **`map_manager`：** 镜像里仍缺；手册中导航点、虚拟障碍物的保存可能依赖它。建图本身已能运行（地图“111”，授权通过）。
- **地图导出：** 地图点云文件在哪里（我们要拿去和 v3 配准）。
- **厂商网页：** 是否自带标点 / 录路径功能；有的话可以一起用，但仍要按第 5 节录一份我们自己的数据。
- **授权与版本：** 授权能否在 eMMC 上生效；`nav:3.2.1.arm.beta` 是否稳定。

### 7.2 安全

- **速度只能有一个来源。** 导航时 `rl_nav` 独占 `/cmd_vel`：不要运行 `s10_ros1_control`，也不要运行 x_nav 的 `w_nav`。
- 我们的 ROS 1 网关是单向的，ROS 1 的 `/cmd_vel` 进不了 ROS 2。
- 录数据时只用遥控器驱动。
- 共用机器人上不要按旧现场助手的“加载地图”，也不要改官方激活地图。

### 7.3 AGX 算力与存储

- x_nav、网关、感知、`rl_nav`、policy 推理共用 8 个核：限制 x_nav 的核数（配置里 `numberOfCores: 8`），并实测负载。
- 原始数据包很大：建图大圈录完尽快拷走。

### 7.4 感知输入

- `rl_nav` 的恢复层需要 AGX 上 ROS 2 的 `/perception/points_yaw` 和高度网格。
- AGX 自己的合并点云应该够用，但要对照仿真里的感知合同核对一次。
