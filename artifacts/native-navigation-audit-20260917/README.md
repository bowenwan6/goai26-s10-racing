# 048 官方内置策略与现有 SLAM 自动导航接入调查

调查日期：2026-09-17，实机观测约 21:17–21:50（北京时间）。已通过 SSH 检查 102、103、106，只读取配置、日志、ROS 接口和状态；没有下发运动、步态、目标点、取消或模式切换指令，没有修改机器人配置。

**结论：适合优先复用官方内置运控，先做现有 SLAM 下的平地自动导航验证。普通、楼梯、高台模式确实在这台狗运行过；全程 Start→终点还需要路线管理、导航步态验证及分段实测。模型是否加密尚不能确定，但调用机身已有运控不需要导出或解密模型。**

## 加密与可用性

- **已确认通信加密**：103 robot_server 日志明确显示关闭明文 TCP/UDP，仅启用 TLS/DTLS，端口 30003/30004。
- **已确认二进制库加载**：官方运控以 .so 形式装载。二进制封装本身不证明模型权重已加密。
- **权重加密未知**：当前 103 SSH 环境是容器视图，日志所示库路径在该视图不可见；有限目录扫描没有找到独立模型文件。因此不能下结论“没找到就是加密”。
- 复用机身内已运行的官方运控，只需使用正常开放的上层接口。把权重拿出来用于我们的 MuJoCo、训练或另一台设备，是不同问题，此次未证明可行。
- AGX 上公开 SDK 工程的 policy.onnx 与本地仿真所用文件哈希不同，且均不能直接认作上述原生运控库。

## 当前导航栈已经具备什么

106 当前激活地图是 `0914_fr_v3-20260914-142008`。localization、planner 服务运行中；安装有 global_planner、traversability_estimation 等组件。

ROS 只读发现了：
- `/GOAL_GLOBAL`、`/GOAL_PLANNER`：`drdds/srv/PoseStampedToInt32`；请求 pose，返回布尔 result。
- `/CANCEL_NAV_GLOBAL`、`/CANCEL_NAV_PLANNER`。
- `/NAV_GAIT`、`/MOTION_SDK_MODE`；仅确认服务存在，**没有验证 command 枚举语义**，不能把 /GAIT 的十六进制值直接套进去。
- `/GAIT`：1 个发布端、2 个订阅端。
- `/NAV_CMD`：2 个发布端、1 个订阅端；短时空闲采样未收到该话题消息。发现发布端不表示它正在发送速度。
- `/MOTION_INFO`、`/HES_STATUS`、`/LOCATION_STATUS`、`/ODOM` 及规划状态话题。

安装的消息定义优先于手册伪代码，例如实际 MetaType 使用 stamp 字段。发现服务和订阅端仅证明接口可见，不等于运动链路已经实测通过。

S10 手册第 49–52 页说明：/GAIT 开放导航平地 0x3002、导航楼梯 0x3003；/NAV_CMD 仅在导航模式生效，建议固定 10 Hz，单位 m/s、rad/s。高台 0x1002 属于基础模式，不能假设它接受相同导航速度输入。

**定位是当前首要前提。** 21:21 的 /LOCATION_STATUS 为 total_status=3；21:49 日志仍报“定位丢失／运行状态=局部”。/ODOM 虽标记 frame_id=map，规划器也报 MapOK/OdomOK，仍不能据此认定已经在 v3 全局地图正确定位。机器人当前是否位于原建图场地尚未确认；若在其他场地，这一状态可能符合预期。

## 建议接入方式

```mermaid
flowchart LR
  S["106：现有 SLAM 与 v3 定位"] --> P["106：已有全局／局部规划"]
  R["102：Start 到终点的分段任务管理"] -->|"目标点、阶段与步态请求"| P
  P -->|NAV_CMD| B["103：原生控制接口与官方运控"]
  S -->|"定位有效性"| R
  B -->|"运动／步态状态"| R
```

先复用厂商规划器，由我们的任务管理程序按路段发送目标、跟踪到达状态及切换步态。102 到这些接口的部署环境与 DDS 配置仍需联调。若原生规划器无法按需要跟随这条复杂路线，再增加自己的路径跟随器，通过同一原生速度接口驱动；这属于后备方案。

主要新增工作：
1. 对齐 v3 地图、实机全局定位和路线坐标；保留高度信息与路段归属，确认 Start 和最终红点。
2. 将 Start→B→大弯→D→复杂楼梯→沥青段→花园终点拆成经验证的有序路段，设置进出楼梯的朝向、速度及通过条件。
3. 验证导航平地、导航楼梯的切换与反馈；高台另行确认支持的控制入口和速度含义。
4. 处理目标成功、失败、超时、定位丢失、人工接管与取消。明确速度控制权：复用厂商规划器时不额外并行发布 NAV_CMD；自写跟随器时再处理与规划／充电控制源的互斥。
5. 分段实测后才串联全程。楼梯朝向、同一 XY 下不同高度、边缘落差和最终花园段的可通过性，都不能由单个终点目标保证。

现有代码还不能直接当作上述接入层：`integration/ros_cmd_interface.hpp` 把 /cmd_vel 接到外部 SDK actor，默认 autostart=true；`real_transfer/shadow.py` 仅为影子验证，不发送实际运动；建图网页的 waypoint 输出也明确 navigation_ready=false。原生日志还显示，外部 SDK 控制期间会忽略外部运动状态指令，需要正确管理两种控制模式。

## 工程量判断

以下是按一名熟悉当前工程的工程师、现场配合充足、接口正常且原场地可测试的**累计粗估**，不是完成保证：

| 阶段 | 预期投入 | 完成标准 |
|---|---|---|
| 原生平地自动导航小样 | 1–3 个工程日 | 正确定位后，从测试起点到少量目标，能取消、能在定位无效时停止 |
| 平地＋普通楼梯的分段原型 | 约 3–5 个工程日 | 明确验证 0x3003、路段切换、进出楼梯朝向及失败处理 |
| MAP 完整复杂路线联调 | 按 1–2 周以上预留 | 每段通过后连续串联；仍取决于高台接口、定位和地形能力 |

**基础接入量不大；全程稳定通过的主要工作是地形与路线联调。** 如果高台没有可用的自主控制接口，或花园段超过官方策略的物理能力，增加上层导航代码也无法保证通过，需要调整路线或获得厂商支持。

MAP 上一轮的 Start 全程仿真仍在 B 失败；后段成功是分段仿真结果，使用的 actor 也不能等同本机原生策略。因此本次只读调查支持“可以开展原生策略导航接入”，不构成 Start→终点已可运行的证明。
