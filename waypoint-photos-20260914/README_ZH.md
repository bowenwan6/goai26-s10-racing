## 结论

这批照片最重要的作用不是“直接产生航点坐标”，而是作为每个航点的**视觉与地形真值**：说明红色标记位于什么表面、附近有什么障碍、机器人应以什么类型的运动通过，以及地图/高度图是否漏掉了关键结构。

照片显示路线大致包含：平整颗粒铺装、草地、石笼高台、连续沥青路、人工低台/黄色凸台、铺装广场、乱石溪床、草石过渡、多个低台阶、弧形楼梯以及建筑旁终点。它不是单纯的平地导航路线。

这些照片可以用于：

1. 将现场红点/红旗与以后记录的地图 XYZ 航点一一绑定；
2. 给航点添加 `flat`、`grass`、`ledge`、`rock_garden`、`stairs` 等语义；
3. 设计每段的限速、对齐、越障策略、绕行限制和失败恢复；
4. 验收 LiDAR 地图是否保留石笼边缘、台阶、乱石和上下平台；
5. 在机器人跑错时，用照片判断是坐标错、路线方向错，还是地形策略选错；
6. 为后续仿真/数字孪生提供外观和拓扑参考。

它们不能单独提供：可靠的地图坐标、精确距离、台阶高度、坡度、航点朝向、可行驶宽度或定位精度。单目照片有透视误差，红点在图像中的像素位置也不能直接换算成机器人地图位置。

## 编号说明

目前按拍摄时间将图片临时对应为 `WP01–WP30`。这是最合理的工作假设，但还不是正式编号证明：部分照片同时拍到了相邻的红点或红旗，而且照片中没有可读的 WP 编号牌。

如果正式规则使用 `WP0–WP29`，则这里的 `WP01` 对应正式 `WP0`，其余顺延。正式使用前应拿主办方航点表或在现场逐点确认一次。

## 对建图和航点采集的直接建议

1. 加载最终地图并确认全局定位后，把机器人停在每个红点/红旗的真实中心，依次保存 `WP01–WP30` 的新鲜定位；照片文件名随记录一起保存。
2. 每个 WP 至少记录地图 ID/哈希、XYZ、航向、楼层、时间、定位状态、地形标签和上一点/下一点。
3. 石笼、黄色凸台、乱石和楼梯点应再拍一张低角度侧视照，并使用卷尺记录高差、台面宽度和可用通道宽度。
4. 单张照片中的机器人朝向只能作为参考，因为拍摄姿态没有标准化；正式 yaw 应由 `上一 WP → 当前 WP → 下一 WP` 的路线和现场安全方向共同确定。
5. WP03、WP15 等同时出现多个红色标记的照片要现场复核，避免把下一点的旗子当成当前点。
6. 照片不替代实机位置采样。当前参考点/子帧尚未核验时，保存的 WP 仍应标记为草稿，不能直接发布自主路线。

## 元数据发现

- 30 张照片按时间连续拍摄，约 11 分钟，支持“沿路线顺序拍摄”的判断。
- 原始照片包含手机经纬度，可作为粗略路线线索，但不能替代 SLAM 坐标。
- 手机高度元数据明显不可靠：相邻平地照片在几十秒内出现从约 -2.6 m 到 76.8 m 等跳变。因此绝不能用 EXIF 高度生成楼层、台阶高度或机器人 Z 航点。
- 预览 JPG 已移除 GPS/高度元数据；原始 HEIC 仍完整保留，便于内部追溯。

## 下一步最有价值的补充

照片与真正导航航点之间还缺一张绑定表：

```text
照片 WPxx
    + 最终地图哈希
    + 机器人停在红点时的地图坐标 XYZ/yaw
    + 楼层与地形标签
    + 前后连接关系
    + 台阶/通道实测尺寸
    = 可审查的真机航点草稿
```

等 30 个点从现场助手导出后，应把导出的 JSON 与 `waypoint-photo-index.csv` 合并，并逐点检查是否存在错序、错层或坐标跳变。
