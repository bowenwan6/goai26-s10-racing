## 结论

当前修复本地通过，未发现本专项剩余阻断。调度缓存仍用调用开始时间，但消息接收 age、源时间 age、状态新鲜度与返回的机器人时间，统一使用取得消息锁后采样的时钟；没有用 `max(0)` 掩盖异常。

新增 `test_snapshot_race.py` 六项，在 Python 3.12 和 3.14 均为 6/6：

| 场景 | 验证结果 |
| --- | --- |
| 非缓存 vendor 查询期间推进时钟并注入新消息 | pose/IMU/cloud/aligned_cloud 接收和源时间 age 均为 +0.05 秒 |
| 已缓存 vendor 状态，但地图身份校验期间注入新消息 | 同样正确，且没有调用 vendor 状态查询 |
| 等待数据锁期间注入消息 | 采样发生在实际取得锁之后，不仅是在 I/O 之后 |
| 真正未来接收时间，缓存/非缓存两分支 | 保留 -0.4 秒，并被定位门禁拒绝 |
| 真正未来源时间，缓存/非缓存两分支 | 保留 -0.4 秒，并被定位门禁拒绝 |
| 慢 I/O 使原先有效状态过期 | 与返回 board_time 一致，fresh=false |

额外在内存中分别注入三个错误实现，测试全部能检出，未修改生产文件：原先 I/O 前采样方式触发 4 个失败；接收 age 强制归零触发 2 个失败；源时间 age 强制归零触发 2 个失败。证明测试不仅接受当前实现，也能拒绝原缺陷与伪修复。

必要回归：原独立套件 Python 3.12 **48/48**（14.617 秒）；实现者的 `test_snapshot_time.py` 经独立运行 **2/2**。`git diff --check` 无空白错误，仅既有 index.html 的 CRLF 提示。本次新 6 项不包含在原 48 项计数内。
