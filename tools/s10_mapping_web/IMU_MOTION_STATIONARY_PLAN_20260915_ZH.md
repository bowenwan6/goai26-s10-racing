# IMU 与静止运动反馈：检查和修复计划

日期：2026-09-15。状态：计划＋本地已有证据检查；尚未实施校准、修改门禁或部署。

## 目标

查清人工确认站稳后，运动反馈持续非零且随时间变化的原因，并修复实际有问题的一层。目标不是让界面数字强制显示0，而是：真实静止可识别、真实运动不被掩盖、定位和原始测量仍可追溯。

## 已确认与未确认

- App 的 `field_robot.py::parse_navigation` 读取厂商 planner 日志 `Motion Vel`，显示 X 速度、Y 速度、yaw 转向速度；第三项不是竖直Z速度，也不是三轴IMU加速度。
- 同一函数要求规划命令与运动反馈全部绝对值小于0.0005，当前还注明字段单位未独立核实。该统一门槛的物理依据不足，存在误判风险，但不能直接按当前最大反馈放宽。
- 本地106历史备份的 YESENSE 配置含串口、200Hz、轴向设置；没有可直接证明硬件是否完成工厂校准的条目。配置中没写零偏，不等于传感器固件里没有补偿。
- 同一备份的 `dr_lio/imu_processing.h` 存在有效的 `IMUInit`、`mean_acc_`、`mean_gyr_`、`imu_need_init_` 和零偏协方差接口。这证明软件有初始化架构，不证明当前运行成功，更不能把协方差参数当成校准偏置值。
- 不知道 `Motion Vel` 最终来自运动控制器、轮/腿状态估计还是建图LIO；建图IMU与运动控制IMU也未证实是同一传感器。
- 本次到 `100.104.52.28:22` 的SSH连接超时，未读取当前开机的配置、初始化状态或实时传感器数据。

## 步骤1：只读核实数据来源和校准状态

1. 恢复可用SSH后核对设备身份、启动时间、软件版本和实际进程加载的配置路径，保留哈希和启动日志。
2. 查清 `Motion Vel` 的发布者、输入、坐标系、单位、日志小数位和更新时间；单独列出原始/已标定IMU、姿态、融合里程计与控制器反馈，禁止混用。
3. 核对实际IMU型号、固件、工厂校准/补偿状态（仅使用厂商支持的只读查询）、在线零偏估计和本次启动初始化完成证据。
4. 查看已有ROS话题和控制器状态；不直接抢占驱动正在使用的串口，不发送重置、归零或校准命令。
5. 闭源实现或缺失状态无法验证时明确记为未知，不通过头文件猜测运行细节。

交付：一张“传感器→处理器→反馈→App”的实际来源表，以及校准/初始化状态证据。

## 步骤2：小范围静止基线，不涉及建图

现场人员先确认机器人安全支撑、停稳，全部policy/导航程序退出，手柄可接管；机器人保持必要的原厂平衡控制，不为采样随意关闭执行器。

- 同步被动记录约2～3分钟：IMU角速度/加速度/姿态、温度（若支持）、源时间戳和接收时间、融合位姿/速度、轮/关节反馈（若可用）、各可见命令源及planner Motion Vel。
- 保留可获得的原生频率，不用网页低频预览代替完整测量。未暴露的原始数据明确标缺失，不触发驱动重配置。
- 按10秒窗口统计均值、标准差、峰值及均值随时间变化；核对日志量化、数据陈旧、断流和实际姿态变化。
- 若当前处于开机升温阶段，记录实际时间和温度，再在稳定阶段重复短样本；不为此次检查擅自重启。
- 只在获得现场同意后，用手柄做3次短距离“动→停”验证，分别观察停止后的收敛。由人操作，不由本脚本发送运动指令。

边界：这是当前静止反馈的有界检查，不重开B平台、全图叠影或历史IMU根因审计。

## 步骤3：按证据选择最小修复

| 检查结果 | 修复方向 | 不做什么 |
| --- | --- | --- |
| 初始化缺失、未完成，或在明显运动中完成 | 按实际厂商机制修复初始化流程；App显示等待/失败原因。重启或重新初始化另行确认后执行 | 不凭头文件常量推断初始化时长，不盲目增加等待秒数 |
| 经确认的陀螺仪静态零偏异常且可稳定估计 | 优先使用厂商受支持的零偏校准/估计接口；备份原参数，先离线验证，再单层应用 | 不同时在驱动、LIO和App重复减偏置；不把本次均值永久硬编码 |
| 偏置随温度/时间明显变化 | 检查既有温度补偿和在线估计是否正常；无法稳定估计则保持失败状态并给出厂商所需证据 | 不用一个常数掩盖时变漂移，不立刻更换IMU |
| IMU无已证实异常，但融合/控制器反馈偏移 | 修复对应估计器的初始化、反馈语义、时序或状态使用；依据可见实现定位 | 不为了消除融合速度去改无证据异常的原始IMU |
| 真实静止下只有已量化的测量残差，App单值门禁误判 | 单独实现持续静止判定：命令源空闲、反馈新鲜、速度/姿态在已验证界限内保持一段时间；进入/退出条件分离，所有原值保留 | 不用“勾选停稳”覆盖非零命令，不按当前最大值自动放宽，不把缺失数据视为静止 |
| 真实微动、控制器振荡或证据不一致 | 保持不放行，报告具体信号，不套用传感器校准 | 不靠均值抵消正负运动、不自动屏蔽平衡控制造成的运动 |

加速度特别约束：静止原始加速度包含重力，不能把三轴都减到0。单个站立姿态不足以可靠求出完整三轴加速度标定；只有确实需要时，另按厂商安全流程安排，不要求用户随意翻转整机。

## 步骤4：实现、验证、回滚

1. 修改前备份实际加载配置与代码，记录唯一修复点；不改频率、LiDAR—IMU外参或v3地图。
2. 用未参与估计的静止样本验证；静止阈值必须有单位、统计依据和安全上限，不是“直到不报错”。
3. 验证3次人工动停：站稳后能稳定进入静止，运动、非零命令、数据过期或定位异常能撤销资格。连续零均值但大幅振荡不得通过。
4. App显示原始数值、等待进度、噪声/漂移判断和阻断原因；不得只显示“IMU正常”。
5. 如果修改了启动/校准流程，在现场同意的维护窗口做一次重启复验，确认本次启动证据和旧检查失效；不把重启后一次归零当成修复成功。
6. 未通过则回滚本次修复，保留原始采样和前后对照，不继续无界调参。

交付：来源/校准检查报告、静止与动停时序图、必要的最小补丁、测试结果和回滚说明。

## 实施顺序与授权边界

先做步骤1及经现场确认的步骤2，再报告明确修复分支。当前请求是检查和计划，不把它视作允许马上重启、写固件、持久化校准或放宽保护。会影响服务的实施需单独确认。

本计划不安排地图更新、重扫、外参调整、机器人自主行走，也不把静止反馈问题与v3几何问题强行建立因果关系。

## 原理依据

- [IMU校准与误差项](https://www.vectornav.com/resources/inertial-navigation-primer/specifications--and--error-budgets/specs-imucal)：用于区分零偏、尺度、轴向和温度效应，不代表本机使用VectorNav硬件。
- [IMU零偏、噪声与重力读数](https://www.vectornav.com/resources/inertial-navigation-primer/specifications--and--error-budgets/specs-imuspecs)：静止不等于所有原始通道数值为零。

Calibration Tools技能用于组织上述检查及区分标定类型；未运行任何实际校准程序。
